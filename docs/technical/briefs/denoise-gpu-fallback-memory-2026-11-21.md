# Why Grade Grain can fall back on the MacBook Neo

21 November 2026 · Windows measurements on `feat/denoise-v1` at `e0257bad`

## What Steve needs to know

Both 42.4-megapixel Sony files stayed on the graphics card in Grade on the PC. So did the nine repeats with the graphics limit set to 2 GiB, the likely Auto setting on the Neo. The closest replay opened the exact copy of `DSC00786.ARW` Steve named, zoomed to 110%, then turned on Clean Grain Small. It drew the exact GPU result in **3.94 seconds**. The Grain fit requested **103 MB** on top of **172 MB** already counted, against a **1,933 MB** limit. That leaves **1,657 MB** of room at this check. The 26-second Mac wait is consistent with the known slow whole-photo CPU preparation. These tests do not establish what sent that Mac session to it.

The Neo's tighter constraint is more likely to be the memory shared by the app, graphics, macOS and other programs. Several Windows runs would be near or above 4 GB if their dedicated graphics memory were charged to the app as RAM. This is evidence of possible pressure, with a wide margin of uncertainty. It does not show that Grade crossed an enforced 4 GB limit or that macOS ran out of free memory. At a 2 GiB graphics setting, none of the explicit Grain reservations came close. Fine and Clean have a separate cold-fit cutoff just above **44.8 MP** for these Sony proportions, regardless of RAM. A 42.4 MP file fits that dimension rule. Micro Grain has region and source restrictions and no comparable whole-photo dimension cutoff.

The first two changes worth trying are to **release graphics memory from old views before starting a new one** and **allow one fresh attempt after a temporary memory refusal**, with a saved reason and figures. Preserve the visible picture while releasing resources it no longer needs. Save the exact fallback reason before changing strip sizes or memory limits. A second possible explanation is a failed strip transfer or graphics validation after the noise measurement succeeded. The successful measurement alone cannot distinguish these causes.

## Test conditions and how to read the numbers

- Unpackaged Windows Electron at 2560 × 1440 with the RTX 4070 Ti, lens off and harsh-speck cleanup ×2.5. The runner's HDR media-query shim selected the HDR presentation path. The test measured memory, routes and exact-frame acceptance, without an HDR display-quality or bad-pixel inspection. One observation per case, with a 10% repeatability band for timings if compared later. Memory samples are approximate and differences inside about 0.1 GB should be treated as unresolved.
- Used scratch copies. The exact 2026 path Steve supplied for `DSC00786.ARW` hashes to `aa6b7118…`, while the same-named manifest file is `6b9781a0…`. The 2022/01 copy matches that manifest, but is a different file and was not substituted. The tested file opens portrait, 5320 × 7968. `_DSC7970.ARW` matches the manifest and opens landscape, 7968 × 5320. Both have 42,389,760 pixels. A comparison with an older Mac receipt that used the manifest's same-named file may therefore compare different pixels and orientation.
- Per photo, Auto ran Clean Small, Clean Large, Fine, then Micro in HDR first and generated SDR second. Each method was selected with Denoise off, enabled at Fit, then zoomed to 110%. The app retained ordinary caches. At 2 GiB the focused run started Clean Large cold at 110%, returned to Fit, then selected Small and repeated through SDR. The last run used another fresh scratch copy and isolated profile for cold HDR Clean Small at 110%. Later actions can hit a ready selector or a cached picture, and a row without a reservation is not a cold measurement. Method timings are indicative action-to-accepted-exact-and-idle times and include up to a polling interval. Import took place outside the per-action windows.
- Temporary diagnostics ran only in the disposable Electron driver. It wrapped `reserveFineGrain` to capture requested bytes and allocations, every resident category, allocator usage and actual budget **before** the call, and the result or thrown reason. It mirrored selected `recordStage` events and listened for uncaptured GPU errors and device loss. It collected app pressure messages (all Electron, GPU, renderer, Python and helper processes), backend preparation and memory events, and relevant HTTP statuses. Windows dedicated/shared readings came from the existing `tools/record-gpu-4d.ps1`. The launcher used the existing DevTools request-body suppression helper. The test applied the existing Settings choice to a disposable profile and supplied `HDR_FINISHER_MEMORY_BYTES=4000000000` to all three launcher commands. No tracked diagnostics or behaviour edits were needed.
- Values below are decimal MB. **PC app** is sampled proportional resident memory across the app tree. **PC dedicated/shared** are Windows process-attributed GPU memory counters. The sampler took roughly two seconds per sample. An asterisk uses the nearest sample for an action shorter than the sampling interval. A dash means no reading or no Grain reservation, as appropriate. Reservation columns show the call with the highest `max(resident, allocator) + requested` within that action. Both most recent and per-call allocator readings are included. The full receipts preserve every call and sampled process.
- **Mac transfer estimate** adds PC app RAM and dedicated GPU memory, using separate within-action maxima as a screening estimate. Shared GPU memory is already in the host memory domain and can overlap these totals. Adding it again would risk double counting. Separate maxima can overstate a coincident peak, samples can miss a transient, and Apple and Windows drivers, compositor, buffer duplication, process charges and viewport differ. Subtract the estimate from 4,000 MB for nominal app headroom. **OS other RAM limit** is how much other RAM usage would leave the 2,000 MB system reserve, `8,589.935 − 2,000 − estimate`. The Windows census cannot tell how much RAM was used by macOS and other apps during the incident.
- Every row finished with the Grade GPU Grain selector. Some POSTs to `denoise-grain` were logged while Grade was on GPU. The matching backend preparations were for **Library**, 640 px long edge, about 0.21–0.45 s, with 4.37 MB scratch. No completed Grade CPU preparation, Grain refusal, HTTP 507, GPU validation fault or device loss was observed. HTTP 409 stale requests occurred during normal replacement and did not trigger a failed-source entry. No GPU failure required a bad-VRAM rerun.

## Where Grade can leave the GPU

Let `W,H` be the developed native dimensions, `N=max(W,H)`, `p,q` the actual Fit processing dimensions, `R` the tracked resident bytes, `U` the allocator's used bytes and `B` the effective graphics budget. Grade treats custom zoom ≥100% as a bounded native view when eligible. At 110% the viewport is the CSS image/viewer intersection mapped into native coordinates, clipped to the photo and expanded by the applicable tile/halo rules. It is not a 1.1× native texture. Fit normally works over the whole reduced image. The fixed margins and strip sizes below are in source pixels.

## Which limit would come first?

- **Graphics admission in these sequences.** At 2 GiB the largest request seen anywhere in the Auto sequence would leave **1,278 MB** of logical room. The largest in the runs actually limited to 2 GiB left **1,507 MB**. Even 1 GiB would have left at least **312 MB** for these observed admission sums with the same residency. A 512 MiB effective budget could deny the later examples with the same cache state, but even that would admit the cold Small 110% fit at the observed occupancy. A broker allowance below **306.2 MB** would deny that cold Small replay. With the same 103.4 MB demand at ordinary 2 GiB, the source would need about **1,829 MB already counted**, compared with 172.2 MB here. Direct driver allocation can fail earlier than this logical check when other work or the OS holds memory it doesn't count.
- **App RAM and system headroom.** Several `_DSC7970` HDR rows screen **52–460 MB over** the 4 GB target ceiling, and generated SDR Micro 110% screens about **340 MB over**. On the exact `DSC00786` file, Auto generated SDR Micro 110% screens **34 MB over**, while the neighboring PDH estimate for Clean Large Fit screens **59 MB over**. Both are smaller than the test's resolution. The closest cold Small replay screens **821 MB below** at **3.179 GB**. - **Photo size.** The first predictable cold Fine/Clean cutoff for this aspect ratio is just over **44.81 MP** (`8192² × 5320/7968`), at either zoom and either generated rendition.
