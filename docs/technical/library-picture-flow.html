Library picture flow

How a photo gets from disk to the screen in the Library, which part of the app does each piece of work, what is kept, and how long each piece takes. Timings as of October 26, 2026, 21:27 session (Steve's app, code through cf47441), read from backend.log with summarize_library_log.py. Where the app run didn't exercise a step, the number is marked profile (Codex's disposable test) or baseline (before tonight's fixes). Grade timings are out of scope except Denoise. The four workers

WorkerWhat it isWhat it does in the Library
PageThe app window (Electron). Runs the Library screen and talks to the graphics card through WebGPU.Decides what to show; keeps finished thumbnails and screen previews in memory; sends drawing, RAW development and Denoise measurement to the graphics card; shows quick draws and sharp draws.
BackendThe main Python process (the same one Grade uses). The only writer of the database and settings files.Serves folder rows from the index; checks and reads the scene cache and stored screen previews; reads RAW sensor data (LibRaw) and decodes JPEG/PNG/TIFF; pulls camera previews out of RAWs and keeps them in memory; saves scene data after a draw.
HelperA second Python process (hdr-library) at below-normal priority, with separate lanes: main, picture, index, check, stored, kept.Background disk checks and indexing; camera details (EXIF); writing stored screen previews (JPEG XL encode); CPU decoding for HEIC/JPEG XL/AVIF. Pauses whenever Grade, import or export is working.
Graphics cardOne shared card. Library drawing, RAW development, Grade, Proof and export all queue for it.Develops RAWs one at a time; measures noise for Denoise; draws every thumbnail and screen preview with the current grade, Denoise, Film Look and HDR/SDR mode.

Everything that is kept

Finished pictures include the grade and HDR/SDR mode and are ready to show. Scene data is developed but ungraded: cheaper than a new development, but it still needs grading and drawing.
