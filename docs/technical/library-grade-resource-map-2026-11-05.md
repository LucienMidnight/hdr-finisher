# Where Library and Grade pixels live

Research for Steve, November 5, 2026. **Review document, not a change proposal or acceptance report.** No app, GPU check, timing run or experiment was run for this research. Code and tests were not changed. This file is deliberately uncommitted for Claude to review.

## 1. Steve's summary

Ordinary Grade editing has a sound shape: keep the developed original in the backend, send a smaller picture to the graphics card, and reuse it. Changing Exposure does not reopen the RAW. Most tools share working pictures. Undo stores instructions, not a photo per step. Leaving Grade deliberately keeps its original open; closing the photo releases it.

The largest costs, in likely order, are:

1. **Opening and redeveloping photos need large CPU working images.** The previous photo remains until the next is ready. Today's lens-correction changes removed a spare full-size colour copy and reduced temporary work, bringing tested Windows handoffs inside the memory allowance. A full correction-coordinate map remains: roughly 1 GB at 42 MP with colour-fringe correction. Larger photos and an 8 GB Mac remain questions.
2. **Library detail crosses back through the backend in the starting version.** Its developed GPU picture is read back, stored, reconstructed in backend memory and uploaded through Grade's transport. Streaming and shared reconstruction improved it, but recorded whole waits remain 6.54 seconds for a 42 MP RAW and 11.81 seconds for a 48 MP TIFF. Another agent is changing this route; these are starting figures.
3. **HSL and hue masks hold substantial working pictures.** Some must be rebuilt when earlier colour adjustments change. Recorded non-default 100% editing remains below its smoothness target. Eligible local colour selections now work on the visible area; combined masks can take a more expensive route.
4. **Returning a saved Grade picture can redraw and transfer a smaller picture.** A clean displayed picture can be captured; some views need a separate render. The other lane still needs finishing. Recent results range from about 0.39 to over six seconds. This normally reuses the original rather than decoding RAW again.
5. **Retouch retains a second full-size original containing repairs.** At 42 MP, original plus repaired result take about 1 GB; replacing the result can temporarily raise this to 1.5 GB before repair working areas. Undo can rebuild that result.

The hidden delivery window's old retention of over 1 GB of completed-job buffers is also fixed. Neither that nor the removed lens copy should be counted as a current leak. Some temporary and graphics-driver memory is measured in process totals but cannot yet be assigned exactly to a cache.

This review makes no blanket GPU or guaranteed CPU-route recommendation. Their costs differ by task. Grade already opens RAWs on the CPU; an earlier GPU trial saved too little of the whole wait. Route decisions remain for Steve's review.

## 2. How to read the inventory

### Evidence and units

- **C** means read from current code; allocation sizes are calculated, not measured live. **M** means a measurement already recorded in the linked product/performance records. **S** means a suspicion requiring measurement. Each table distinguishes these.
- Research anchor: `main`, HEAD observed as `0d3854f`. This is a shared, changing checkout. Function names are the navigation authority; line numbers and concurrent zoom code may move. Zoom's GPU-first brief is work in progress, not proof it has shipped. The initial status also contained an unrelated untracked `docs/design/grade-notice-wireframes/` directory, left alone.
- MB and GB below are decimal. One megapixel is one million pixels. A calculated 42 MP example is not the exact Sony fixture: that fixture's approximately 42.4 MP RGB source is recorded as **508.7 MB**.
- **N** = original source pixels; **P** = pixels in the requested preview; **R** = visible region/tile including its required surrounding pixels. Costs expressed per P or R must not be multiplied by the whole original unless the route actually works at that size.
- Multiple names/views of one NumPy root or one texture are **one backing allocation**. Original, processed, masks, staging and presentation pictures are different representations, not all unnecessary duplicates. Counts below state known owners and conditional overlap; they are not an asserted complete process peak.

| Representation | Bytes/pixel | MB per MP | At 42 MP | Where normally used |
|---|---:|---:|---:|---|
| RGB float32 | 12 | 12 | 504 MB | Backend scene original, repaired result, CPU processed frame |
| Two RGB float32 frames | 24 | 24 | 1.008 GB | Original + repaired, or old + new source |
| RGB float64 | 24 | 24 | 1.008 GB | HSL CPU numerical working picture |
| RGB half-float | 6 | 6 | 252 MB | Stored scene samples / some transfers |
| RGBA half-float | 8 | 8 | 336 MB | Typical GPU source, grade and presentation texture |
| RGBA float32 | 16 | 16 | 672 MB | Exceptional source transport, HSL/denoise scratch |
| Scalar byte / half / float32 | 1 / 2 / 4 | 1 / 2 / 4 | 42 / 84 / 168 MB | CPU cached mask / GPU mask / processing mask or luma |
| XY float32 / RGB-channel XY float32 | 8 / 24 | 8 / 24 | 336 MB / 1.008 GB | Lens distortion / chromatic correction coordinates |

For scale: a 1600 x 1067 RGB32 picture is about 20.5 MB, its RGBA16 GPU texture 13.7 MB. A 2560 x 1707 RGBA16 picture is about 35 MB. Rows crossing the GPU boundary can include padding to 256 bytes. Compressed files have no fixed bytes/pixel; OS/driver overhead is additional.

### Accounting shared by all tables

The [memory PRD](../product/modules/memory-and-caches.md), sections 4–6, owns the limits. At the default 4 GB setting: whole-app RAM ceiling 4.0 GB, accepted short peak 4.4 GB, settled target below 3.4 GB, with 600 MB working headroom. Retained Grade source bytes are reported separately as document ownership, **not added again** to process RAM. Grade cache arrays and retained backend native detail share the aggregate **600 MB working retention** allowance; it is not a 600 MB maximum job size. Other shares: thumbnails 512 MiB, sharp scenes/surfaces 512 MB, camera pictures 64 MB, RAW read buffers 768 MB, handoff 256 MB. Some shares scale with the chosen whole-app setting.

Dedicated GPU memory is separate on Steve's Windows machine. Grade's pure planning default is 2 GiB; the desktop/broker supplies the effective device budget, with Library reporting the same effective budget. Do not substitute that policy constant for measured available VRAM. On an integrated/unified-memory machine GPU memory competes for RAM. Windows shared-GPU counters may overlap host pages: do not add them blindly to counted RAM.

The cache ledger is not a heap census. Temporary decoder/filter arrays, HTTP/JS buffers, repair history and native driver pools may lack individual cache claims yet still appear in actual process RAM. Within-session array roots are deduplicated; that does not establish a universal cross-process allocation census. `app_memory.py`: `budgets`, `claim`, `cache_snapshot`; `sessions.py`: `_publish_retained_session_bytes`; `render_cache.py`: `_retained_bytes_locked`.

## 4. Open questions and suggested measurements

No new run is requested as part of this research. The other agent owns app/GPU testing now; **do not overlap it**. These are possible later measurements for Steve to choose after review, not a test sweep or a new acceptance policy. For any new timing comparison, record the tolerance before measuring; use existing agreed tolerances where applicable. No pixel/timing/memory limit is relaxed by this document.

1. **What survives today's zoom work?** Re-read its committed source and result first. Update flow E and candidates before commissioning another zoom run. Confirm direct source ownership, source-coordinate/mask/denoise behavior, Compare, cancellation and CPU recovery from that agent's evidence. This research does not certify their implementation.
2. **What is the actual whole wait for Grade A -> Grade B?** Existing records contain import totals, first-frame timings and paired contention checks under different conditions. They cannot be merged into a universal latency. A focused trace should start at user action and end at accepted visible frame, separate original read/hash, decode, lens, conversion, upload, GPU and presentation, and label old-source overlap.
3. **Does all original storage have an owner?** Audit `LivePictures._held`, active repair patch/job arrays, history/redo and transport buffers against named claims and whole-process totals. `SessionRenderCache` explicitly excludes document source roots; a synthetic Library native frame is not automatically the active Grade document. Establish which source grant still covers each route and whether expiry/revocation leaves an uncharged live frame. “Outside cache ledger” does not mean “outside measured RAM.”
4. **What is the peak when expensive Grade features combine?** Existing latest four-handoff peaks pass for the tested RAWs. That does not cover active HSL plus hue masks, Denoise, several repairs, extreme geometry or 100 MP+ originals together. A focused owner census of a representative saved grade is more useful than a whole driver sweep. Do not sum maxima from independent runs.
5. **Are whole-frame source/presentation stores paying for themselves?** Grade's pan store has recorded benefit; Library native draw resets its session. Measure the actual source-upload reuse and pan latency in each context before assuming one retention policy fits both. For images wider than adapter limit, record which route is really used.
6. **Why is later HDR Grade handoff much slower?** Recent records show both sub-half-second and six-second results. Separate waiting for current scope picture from capture and storage; popout transfer is another condition. One slow sample is not proof screen encoding alone owns the wait.
7. **What can the CPU route promise?** Inventory supported source/feature/size combinations, peak temporary memory and fallback disclosure. Existing forced-recovery evidence has known high-memory CPU cases. Decide separately whether any route is required to finish, allowed to use reduced resolution, or allowed to refuse with a clear message. Steve has made no new guarantee here.
8. **What fits on the 8 GB Mac?** Existing Windows-derived envelopes are estimates, not Metal/unified-memory measurements. A real Mac run needs physical-footprint accounting that does not double count shared graphics pages. Existing smaller-machine limits remain in force.
