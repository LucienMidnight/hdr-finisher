## Measured run B2-1 and extrapolation

**Measured, 2026-11-13:** Ryzen 5 7600, RTX 4070 Ti 12,282 MiB, installed RAM 67.82 GB (CIM and nvidia-smi). Isolated Python 3.12 environment, ORT DirectML 1.24.4; two CPU intra-op threads, below-normal process priority to avoid disturbing other researchers. This is a modest benchmark cap, not proposed product scheduling.

Read existing JPEG/PNG copies recursively from the main checkout's `codebase/output/test-photos/`, deduplicating name/size pairs. Found 107 inputs, including synthetic gradients and repeated renditions. Made oriented RGB JPEGs bounded to 640 px in scratch; no Library-cache/original writes. Benchmark opens each JPEG, decodes, bicubic-resizes shortest edge to 224, center-crops, normalizes, infers a 512-vector and normalizes it. Sources with no ready thumbnail were not developed. Timing excludes the one-off scratch-thumbnail preparation, downloads, database persistence and UI presentation. OS cache was not flushed. Therefore this is a **warm local-thumbnail pipeline**, not a measured cold 10,000-photo user wait.

**Measured:** initial 107-photo CPU run 6.769 s plus session load 0.329 s, median 58.6 ms/photo, p95 93.6 ms, peak sampled process RSS 424.7 MB. Initial DirectML run 5.676 s plus load 1.132 s, median 13.2 ms, p95 18.5 ms; first execution/compilation dominates its aggregate. Peak process RSS 633.5 MB includes subsequent CPU text execution. Some graph nodes ran on CPU. Dedicated VRAM attribution was not collected: do not equate host RSS with VRAM.

**Measured:** a longer CPU run cycled the 107 files three times (321 embeddings, not 321 distinct photographs): 22.801 s plus load 1.868 s; median 64.8 ms, p95 113.6 ms; peak RSS 426.3 MB. Shared-machine contention and warm repeat reads prevent precise scaling. Warm CPU query encoding plus scan over this tiny corpus was 34–49 ms; first short run 25–61 ms. A separate CPU text-only process measured model+tokenizer load 369 ms, first unpadded short query 6.2 ms, and RSS 335.4 MB after execution. This is one warm-filesystem sample; padded 77-token queries in the main harness cost more. An initial probe supplied an unsupported attention_mask input; using only the graph-declared input fixed it.

**Estimated:** 10,000 thumbnails at the 321 CPU-run mean need 710 s (11.8 minutes) plus startup, persistence and any unavailable-thumbnail work. Initial DML aggregate projects 530 s (8.8 minutes), while warmed median alone suggests 132 s; that gap makes a GPU speed promise unjustified. A second **measured** DirectML run completed 321 embeddings (107 inputs repeated): load 0.506 s, loop 2.968 s, median 8.71 ms, p95 9.71 ms, sampled peak RSS 612.4 MB. Its aggregate projects 92.5 s (1.54 minutes) for 10k plus startup/writes/pauses. This warmed repeat-input result needs a cold, distinct-image test. These are arithmetic extrapolations, not full-folder timings. Whole wait is model startup + local thumbnail read/decode + inference + durable index writes + UI result publication + foreground pauses. Cold local storage and missing thumbnails remain unmeasured. Never quietly add RAW decoding to this estimate.

**Estimated:** Apple silicon CPU fallback planning envelope 0.05–0.25 s/photo (8–42 minutes/10k); CoreML planning envelope 0.01–0.10 s/photo (2–17 minutes/10k), plus startup, I/O, writes and pauses. These intentionally broad hypotheses apply only to the B/32 baseline; no Mac was available. They cannot rank SigLIP, PE or RAM++. On an 8 GB Mac the whole-app 2.5 GB default makes eviction/unloading mandatory. No model-specific Apple timing is established.

## Storage, updating and scheduling design

Everything in this section is **estimated/proposed**, constrained by technical Library `:50`, `:63`, `:254`, `:630`, `:650`, `:666`, `:811` and PRD philosophies above.

Keep rebuildable embeddings in a separate `library-ai.sqlite3` beside `library.sqlite3` under the existing app-data root, not beside originals. Use ordinary BLOB rows first: stable photo identity, source version, thumbnail/content key, grade/crop generation, model digest, preprocessing digest, dimensions, precision, vector, status and timestamp. Separate DB avoids bloating authoritative marks transactions; batch short WAL transactions and atomically publish only a complete vector. Missing/corrupt DB means search preparation is needed, never lost accepted tags. Do not make vectors part of sidecars.

Normalized 512-d fp16 is 1,024 bytes/photo: 10.24 MB/10k or 102.4 MB/100k. Int8 is 512 bytes plus scales: 5.12/51.2 MB. For 768-d fp16, 15.36/153.6 MB; 1024-d fp16, 20.48/204.8 MB. These exclude SQLite pages, keys, WAL and staging. Int8 must be independently ranked against fp32; do not assume quantization preserves near-ties. A chunk converted to fp32 adds 4 bytes/dimension in RAM.

Start exact CPU dot-product scans at 10k (5.12 million dimensions/query for 512-d). At 100k scan 51.2 million dimensions with bounded chunks; benchmark cold and warm before adding an index. A separate mmap vector file complicates row/version atomicity; avoid initially. SQLite BLOB plus NumPy is enough to test feasibility, but measured synthetic RAM-only scan plus top-20 selection (five repetitions, fp32, two OpenBLAS threads) took 0.14–0.79 ms at 10k and 5.97–7.41 ms at 100k. Inputs were constant synthetic rows, so this qualifies neither real ranking nor database/filter/cold-load latency. If needed, sqlite-vec offers an extension-based exact scan (MIT/Apache options, [licences](https://github.com/asg017/sqlite-vec)); hnswlib offers approximate HNSW (Apache-2.0, [licence](https://github.com/nmslib/hnswlib/blob/master/LICENSE)); Faiss exact/approximate implementations are MIT ([licence](https://github.com/facebookresearch/faiss/blob/main/LICENSE)). HNSW adds graph memory/rebuild complexity and filtered-recall risks; Faiss adds native packaging. Pick neither until exact search misses the latency target.

Embed the existing local 640 thumbnail or an already-cached oriented camera preview, converted consistently to bounded SDR RGB. Do not feed an HDR transfer function directly into training normalization. Missing input stays pending until normal Library work prepares it or the user explicitly requests preparation; readiness must not force reads from a slow photo drive. Report indexed/eligible/pending counts. Semantic results use cached Library identities/facts; background batched folder checks reconcile later.

New input queues once. Source replacement invalidates the vector; an edit/crop invalidates its appearance generation after save and local thumbnail publication. Pending grades must not overwrite a saved generation. Rename/move preserves stable identity and retargets path metadata; where identity is uncertain, use existing file-command reconciliation rather than hashing every original on query. Virtual copies may share identical input vectors until their appearance differs. Model/preprocessor upgrades create a new generation and re-index; never compare vectors across generations. Switch atomically when ready, with progress/cancel/resume, and keep accepted tags intact.

Use a dedicated unloadable AI helper accounted by the existing memory broker. Low-priority jobs yield between photos/bounded batches to Grade, export, Proof and visible Library work; honour indexing Pause/off. Admit actual model/runtime host pages and graphics allocation through existing budgets; no private GPU budget and no silent budget increase. Scale idle CPU work within memory admission, without a permanent two-thread product cap. GPU attempt once then CPU fallback under the existing failure rule; preemption is resumable, invalid output is not retried on GPU. Keep inference separate from the Library control/index lane so a slow model cannot stall marks saving. On pressure, discard queued tensors then unload image session/helper; text session should also be evictable.

Tag UI: show a short “Suggested tags” group with Add, Dismiss and Add selected. No automatic sidecar writes, no Smart Album membership based on unaccepted suggestions. Acceptance uses the existing marks/undo/durable-sidecar path; dismissal is derived model/vocabulary state. Cache vocabulary embeddings per model; encode prompts such as “a photo of a red car”, calibrate each label and allow no suggestion. Rejected suggestions must not keep returning for the same generation.

## Packaging and first step

**Read:** ORT provides [DirectML](https://onnxruntime.ai/docs/execution-providers/DirectML-ExecutionProvider.html) and [CoreML](https://onnxruntime.ai/docs/execution-providers/CoreML-ExecutionProvider.html) providers; these do not guarantee every graph executes entirely on the accelerator. **Estimated:** deploy pinned split graphs in a Python helper with ORT CPU everywhere, DirectML Windows, CoreML Apple silicon after graph qualification. Flatpak should start CPU-only; optional GPU providers require separate driver/sandbox validation. PyInstaller must collect provider DLLs/shared libraries, tokenizer data and notices explicitly. Electron sends only job IDs/results to the backend; no Node inference dependency is required. Offline model packs need versioned manifests, SHA-256 verification and a local-import path. No network at query time. No installer or packaging experiment was run.

**Estimated first step:** build a disposable harness, not app integration: 300–500 distinct representative thumbnails, relevance labels for 30 queries including missing subjects, and a pinned SigLIP 2 Base split-ONNX export against this CLIP baseline. Time cold load through committed rows/results, measure process-tree RAM and dedicated GPU memory, then test CPU fallback and an 8 GB Apple-silicon Mac. Only after that choose a model and ask Steve to allocate an AI cache/share. This report does not justify adding one now.

## Risks, proposed tolerances, open questions

**Estimated tolerances for the next measurements:** timing variation ±15% across three matched runs, because shared-machine noise is visible; warm query-to-results p95 =250 ms at 10k and =500 ms at 100k, because search must feel interactive; yield to foreground within 250 ms between jobs, because background inference must not delay grading; whole-app peak/settled limits remain the existing +10%/minus-600 MB rules, with no relaxed reserve; quantized top-10 overlap =95% against fp32, because savings must not noticeably scramble results; judged relevant result in top five for =80% of positive queries and =90% precision for displayed tag suggestions, because wrong tags create cleanup. These are proposed pilot gates, not approved new product requirements. Negative-query abstention needs separate calibration.

**Estimated risks:** false positives, compositional/color/negation errors, edge loss from crops, bias and sensitive-label suggestions; cache eviction leaving incomplete coverage; stale edits; model licensing/provenance; unmeasured GPU allocation and cold startup; 8 GB Mac headroom; native provider/Flatpak packaging. No training-dataset redistribution is proposed, and a permissive weight card does not independently clear training-data rights.

Open questions: Which languages and subjects matter to Steve? Search saved appearance or original subject? How many distinct images at 100k versus virtual copies? Can users choose an optional model pack? What disk allowance and memory ownership can AI receive without reducing thumbnail readiness? Is an explicit preparation step acceptable when no local thumbnail exists? Do the newer small PE/EmbeddingGemma options beat SigLIP 2 on Steve's labelled photographs?
