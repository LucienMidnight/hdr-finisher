## Item 8: marks waiting during rename/move/delete

**Cause.** **Read in code:** two distinct global locks matter. `library_file_commands.py:109` holds the writer lane and marks lock during rename/move planning, including source hashes (`:135`). `_run_reserved` holds `marks.writer._lane` across the entire batch (`:338-395`). `move_item` holds `marks._lock` during retarget and `pictures()` (`:264-277`); Delete does the same (`library_file_delete.py:117-120`), and folder operations additionally hold browser/index locks (`library_file_folders.py:151`). `library_marks.py:436` needs the marks lock to accept a change; `library_settings_writer.py` needs its writer lane to write pending settings. Thus both durable acceptance and eventual sidecar writing can wait. This is not merely a long SQLite transaction: `library_file_state.py:59-75` closes the retarget transaction before the archive work.

**Read in code:** `library_file_state.py:88-112` enumerates every `.npz` and reads its JSON metadata to discover matching paths. Rename/move then decode and recompress matching archives, stat the destination, replace files and update the cache ledger. Delete skips pixel decode but still scans all archive metadata. These operations remain inside the global protection above. Slow storage magnifies planning hashes, file moves and archive reads; unrelated marks should not inherit those waits.

**Measured, existing large-cache evidence:** `docs/technical/performance-table.md:2534-2570` records 5,475 cache files / 966 MB. After the 0.9.2 bookkeeping repair, backend plan-plus-execute is Rename **1.001–1.074 s**, Move **0.789–0.803 s**, Delete **0.968–1.398 s**, two trials each. Earlier warm commands were roughly 4.2–4.3 s; removed reconciliation alone cost 3.313–3.482 s. The separate cold-copy Rename was 20.813 s before that repair. These use a tiny disposable original and Bin substitute, and exclude redraw, real RAW hashing and Windows recycling. Referenced W3 raw timing files are not present at the main-checkout paths now, so these values are documentary evidence, not independently reanalysed raw samples.

**Estimated wait:** an unrelated marks request arriving during the cache-lock section waits for its remaining duration; a settings flush may wait for the remaining whole batch. The warm command ranges establish the approximate one-second operation scale, not an exact concurrent marks-save latency. Large batches and slow-drive hashes can extend settings blocking well beyond one second. An exact current large-cache marks-click-to-sidecar maximum was not measured and must not be inferred from the command table.

**Proposed fix — indexed cache work outside global locks, using the existing single writer.**

1. Extend the disposable cache ledger, not the authoritative marks database: `source_entries(cache_file TEXT PRIMARY KEY, source_key TEXT NOT NULL, source_path TEXT NOT NULL, kind TEXT NOT NULL, identity TEXT NOT NULL, generation INTEGER NOT NULL)`, with an index on `(source_key, cache_file)`. Root is implicit in that ledger. Canonical source keys must follow existing Windows path/case and virtual-copy semantics; retain original spelling separately. Folder lookup must use an indexed, separator-bounded prefix or enumerate indexed children, never an unescaped SQL LIKE pattern.
2. Register picture/default-document/overlay variants at atomic publication, remove entries at eviction, and cover retarget, cache relocation and reset. Relevant publication sites: `library_pictures.py:118-119,225-226,341-342`, `library_overlays.py:370-371`; existing ledger transactions are in `library_cache.py:188-210`. An index entry must describe the published file, not merely planned work.
3. Keep file-command durable records and per-source reservations through reconciliation. Snapshot/recheck under short global locks; perform affected archive IO outside marks and outside the global writer lane. Existing writer blocked-path checks can skip affected paths while unrelated settings proceed. Release/reacquire between items only with revision checks, never write an old snapshot over newer marks. File planning hashes also need a protected-snapshot/revalidation split to meet slow-storage independence.
4. Serialize cache publication/retarget per source and generation. Reject a publication prepared before a move/delete; do not let it recreate an old-path entry after cleanup. A filesystem replacement and SQLite commit are not one atomic transaction: missing/stale index rows after a crash must be treated as cache misses, validated against embedded metadata, and reconciled by a bounded background rebuild. Rebuild from final archive metadata, ignore temporary files, prune absent files, atomically publish a completed rebuilt index, and replay durable file-command records before permitting affected publications. Never rebuild marks or grades from cache metadata. Missing cache entries may cost recomputation, never authored data.

**Cost.** **Estimated:** O(log N + affected entries) lookup replaces O(N) metadata opens. A few indexed metadata rows per photo and one bounded ledger update per publication; roughly a few MB for 5,475 entries depending on path length/page utilization. Rebuild remains O(N) but runs in interruptible background batches. Matching archive compression remains proportional to affected pixels and can still be slow; the index does not remove it.

**Rejected alternatives.** Shorter SQLite transactions alone do not release either Python lock. A second writer risks same-sidecar races and lock-order deadlocks; the existing lane plus affected-path exclusion is simpler. Returning success before an untracked scan creates stale-path publication and crash-recovery holes. Background cache work is acceptable only as recorded, fenced work, with explicit completion semantics. Invalidating every cache entry instead of retargeting is simpler but can turn a cheap rename into photo-drive rereads/redevelopment, conflicting with slow-storage browsing. An initial smaller step is moving the scan outside global locks with source fencing; it fixes unrelated marks contention but leaves command completion O(N), so it is not the final recommendation.

**Expected gain on the whole wait.** **Estimated:** unrelated marks acknowledgement should lose the residual cache-scan wait, potentially most of a roughly one-second warm command overlap; sidecar writing should no longer inherit a whole unrelated batch. Rename/move/delete completion also loses unrelated archive discovery, but preserves file IO, safety hashes, affected compression, Windows recycling and redraw. No justified end-to-end percentage is available; do not promise another 4× improvement or under-one-second slow-drive completion.

**Effort.** **Estimated:** 12–20 agent-hours for complete publication/eviction/index/rebuild coverage, lock splitting and concurrency/crash tests; 4–8 for focused app/slow-storage validation. A safe lock-scope-only first step is about 6–10 hours but does not solve cache-size scaling.

**Risk.** Stale publications, cache rows under an obsolete path, folder-prefix collisions, missed virtual-copy variants, lock-order deadlocks and interrupted cross-drive moves. Authored sidecars, queued marks/grades, Undo, recovery records and clash refusal must remain authoritative. Cache repair can discard cached pixels; it must never discard pending authored work or report a partially completed destructive command as fully finished.

**Test plan.** Node/Python fast checks; focused `test_library_file_commands.py`, `test_library_file_delete.py`, `test_library_file_folders.py`, `test_library_file_exfat.py`, `test_library_cache.py` and settings-writer tests. Add fault injection after archive replace/before index commit, concurrent publish-vs-move/delete, Unicode/case-only paths, prefix boundaries, copies, missing/corrupt ledger, relocation, rebuild and Undo. Block cache IO deterministically and prove an unrelated mark is durably queued and reaches its sidecar before releasing that blocker. Then shared-lock `library-photo-file-commands.js`, `library-delete-file-commands.js`, `library-folder-file-commands.js`, grouped as appropriate, plus one default quick Library smoke. Measure click-to-acknowledgement and click-to-sidecar separately during single and bulk commands on a disposable 5,475-entry cache and slow-storage originals; no real Library writes. Stop before exceeding 30 graphics minutes.

**Proposed tolerance.** Retain the existing 250 ms background marks-lock goal and single-photo under-one-second completion goal; propose unrelated mark acknowledgement within 250 ms and durable sidecar completion within one second when its own storage is available, because unrelated file work should add no human-visible pause. Report slow/offline settings storage separately rather than hiding it in the command timing.

**Confidence.** High on lock ownership and full-cache scanning; medium on the design; low on an exact whole-wait gain until concurrent marks and real slow-drive completion are measured.
